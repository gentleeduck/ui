<Callout icon={<Target />}>

The clean migration path is: move static values into config, move outputs to a consumer-owned config root, then reattach optional behavior as explicit extensions.

</Callout>

## Migrate from hardcoded builders

If your current build still hardcodes source arrays, output directories, theme data, or framework logic in code, migrate in this order:

<Steps>

<Step>Extract static inputs</Step>

Move registry entries, colors, themes, and source-path declarations into config or external JSON/TS data files.

<Step>Create a consumer-owned config</Step>

Place `registry-build.config.ts` beside the app or package that owns the generated outputs.

<Step>Map item types explicitly</Step>

Define `sources`, `targetPaths`, `packageMappings`, and `schema.itemTypes` using the same ``registry:${string}`` namespace.

<Step>Keep the core small</Step>

Enable the base build first: `index` and `components`.

<Step>Reattach optional behavior intentionally</Step>

Add `validateExtension()`, `componentIndexExtension()`, `colorsExtension()`, or your own custom extensions as needed.

<Step>Verify outputs</Step>

Diff the generated outputs against the old pipeline and classify each difference as either intentional cleanup or regression.

</Steps>

## Typical before and after

### Before

- hardcoded arrays of registry entries in source
- `.env` values for source/output paths
- framework-specific import generation mixed into the main build
- one repo layout assumed forever

### After

- typed config as the source of truth
- path-aware `extends`
- explicit extension list
- consumer-owned output root
- CLI execution from the consumer package

---

## Monorepo migration checklist

- move the config to the consuming app/package
- resolve all paths relative to the config file
- keep registry data in JSON or typed modules
- replace switch statements with `targetPaths` and `packageMappings`
- move optional outputs behind extensions
- ignore `.registry-build/`
- add one package script that runs `registry-build build`

## Common mistakes

<Accordion type="multiple" className="w-full">
  <AccordionItem value="cwd-vs-config">
    <AccordionTrigger>Confusing config-relative paths with current working directory</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">

Always think in config-relative paths. The loader normalizes them immediately, so `sources.path`, `output.dir`, `registrySource`, and external colors/themes data should all be declared from the config file's point of view.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="too-many-defaults">
    <AccordionTrigger>Expecting hidden default plugins</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">

The package does not attach validation, component-index generation, colors/themes, or banners automatically. If you need them, add the extension explicitly.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="stale-cli-flow">
    <AccordionTrigger>Keeping old repo-local wrapper scripts around</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">

Once the package is installed as a dependency, prefer `registry-build build` in your package scripts. The consumer should use the CLI normally instead of reaching into package internals.

    </AccordionContent>
  </AccordionItem>
</Accordion>

---

## Final verification checklist

- `registry-build build` succeeds from the consumer root
- the generated index is stable across two warm runs
- no-op warm builds report zero rewritten files
- changed-only runs only touch expected artifacts
- `.registry-build/` stays ignored by Git
- the docs or downstream consumer still builds with the generated outputs
