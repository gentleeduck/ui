## What this package is

gentleduck/registry-build is a consumer-owned build system for registry-style content.

Use it when you need to:

- discover files from one or more source trees
- attach structured metadata to those files
- emit a stable machine-readable index
- generate derived outputs such as component indexes, theme files, or custom manifests
- keep the build reproducible and configurable instead of hardcoding monorepo paths

The package is intentionally split into a small core and explicit extensions. That keeps the base runner reusable while still supporting docs-site style builds.

---

## Why it exists

The old approach to registry generation usually looks like this:

- arrays of entries hardcoded in source
- output paths hidden behind environment variables
- framework-specific logic baked into the build
- one repo layout assumed forever

registry-build replaces that with:

- a typed `registry-build.config.ts`
- path-aware config composition with `extends`
- explicit extension hooks for optional outputs
- CLI-driven execution
- incremental caching for repeated local builds

## Capability map

| Layer | Responsibility | Why it matters |
| --- | --- | --- |
| Config loader | Discover config, resolve `extends`, normalize paths | Consumers own the build contract |
| Core phases | Build `index.json` and per-item JSON outputs | Stable machine-readable artifacts |
| Extensions | Add validation, banners, component indexes, colors/themes, or custom outputs | No hidden default plugins |
| CLI | Run builds from app/package roots | Works like a normal tool, not a repo-only script |
| Performance layer | File-hash cache, write skipping, changed-only mode, bounded concurrency | Fast warm builds and less filesystem churn |

## Core model

<Accordion type="multiple" className="w-full">
  <AccordionItem value="consumer-owned-config">
    <AccordionTrigger>Consumer-owned config</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">

The config file lives beside the app or package that owns the outputs. That means source paths, registry entries, output directories, extensions, and performance settings are all declared by the consumer, not buried inside the shared package.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="core-vs-extensions">
    <AccordionTrigger>Core phases vs extensions</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">

The core runner only knows how to build the base registry index and per-item JSON artifacts. Validation, component-index generation, colors/themes, and banners are attached explicitly as extensions. If you do not attach them, they do not run.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="typed-registry-namespaces">
    <AccordionTrigger>Typed registry namespaces</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">

Registry item types are validated as ``registry:${string}``. The same namespace carries through `sources`, `targetPaths`, package mappings, schema item types, and inline registry entries. This keeps config composition consistent as the build grows.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="incremental-builds">
    <AccordionTrigger>Incremental rebuild behavior</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">

The builder stores cache data under `<output.dir>/.registry-build/`. On warm runs it reuses file hashes, skips unchanged writes, removes stale generated files, and can narrow work further with `--changed-only` plus explicit changed paths.

    </AccordionContent>
  </AccordionItem>
</Accordion>

## Typical use cases

- Build a docs-site registry from component source folders.
- Emit an installable JSON index for a CLI.
- Create a generated component import map for a framework.
- Generate theme and token payloads from static data files.
- Produce custom artifacts through extension hooks after the base registry is materialized.

---

## Production checklist

- keep the config beside the output-owning app or package
- declare every registry item type explicitly through the same ``registry:${string}`` namespace
- use extensions only for optional or logic-bearing outputs
- verify two consecutive warm builds produce zero rewritten files when nothing changed
- keep `.registry-build/` ignored by Git
- add typecheck, docs-content build, and at least one real consumer smoke test to CI
